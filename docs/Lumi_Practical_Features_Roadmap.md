# Lumi 언어 실용화 로드맵

> **이 문서는 무엇인가**: Lumi(루미)를 실무와 실제 프로젝트에서 쓸 수 있는 언어로 만들기 위해 **무엇이 이미 됐고, 무엇이 남았고, 어떤 순서로 해야 하는지**를 적어 둔 문서입니다.
>
> **마지막 갱신**: 2026-08-10 (4단계 반영 — IDE 크로스 플랫폼만 남음). 그 전: 2026-08-09 (2단계 완료 반영) — 소스를 실제로 읽고 돌려 본 결과를 반영해 전면 재작성했습니다. 예전 판의 "앞으로 할 일" 중 상당수는 이미 끝나 있었고, 반대로 예전 판이 몰랐던 치명적 문제(예외 처리가 통째로 작동하지 않음)가 있었습니다.

---

## 1. 지금 어디까지 와 있나

| 항목 | 상태 |
|---|---|
| 실행 엔진 | C 로 만든 **AST 트리워크 인터프리터** (`c-interpreter/`) |
| 성능 | 100만 번 루프 0.20초, `fib(27)` 0.45초 — CPython 과 비슷하거나 빠름 |
| 메모리 | 참조 카운팅 + **순환 참조 수집기**(`gc_collect`) |
| 문자열 | 코드포인트 배열(UTF-32). `len("한글")` 은 2 |
| 딕셔너리 | 순서를 지키는 **해시 테이블** (O(1)) |
| 개발 환경 | Lumina IDE (C++/Qt6) — 윈도우 확인 완료, **리눅스·맥은 빌드는 되나 미검증** · VS Code 확장(LSP + 디버거) |
| 돌아가는 곳 | 인터프리터: 윈도우 / POSIX **둘 다 빌드·테스트 통과** · IDE: 윈도우 확인 완료, 리눅스·맥 미검증 |
| 회귀 테스트 | `tests/run.bat` (윈도우) · `tests/run.sh` (리눅스·맥) · GitHub Actions — 예제 62개 **＋ 언어 단위시험 109개 ＋ lint/fmt 골든 ＋ DAP 대화 골든 ＋ HTTP 서버 시험 7개** |

### 이미 끝난 것 (예전 판에서 "앞으로 할 일"이었던 것들)

- ✅ **예외 처리** — `try` / `catch` / `safe` / `always` / `error(...)`
- ✅ **JSON 내장** — `json.parse` / `json.stringify`
- ✅ **패키지 매니저** — `lumi pkg init/install/remove/list/update/info`, `lumi.json`
- ✅ **해시 테이블 딕셔너리** — 선형 탐색은 이미 없어졌습니다
- ✅ **모듈 네임스페이스** — `bring amod` → `amod.hello()`. 순환 import 안전
- ✅ **컬렉션 컴프리헨션** — `[x * 2 for x in xs]`
- ✅ **`sys.args`** — `args()` / `args(자리)` 로 구현 (아래 4.3 참고)
- ✅ **스택 트레이스** — 오류에 파일 이름과 호출 자취가 붙습니다
- ✅ **크로스 플랫폼** — 리눅스·맥 빌드 (`build.sh`, `CMakeLists.txt`)
- ✅ **1급 함수 호출** — `목록[0](10)`, `바깥(5)(3)`, `표["키"](7)`

### 방향이 바뀐 것

- ❌ **바이트코드 VM 전환** — **취소했습니다.** 만들다 만 VM 이 예외 처리를 통째로 망가뜨리고 있었고(오류 핸들러 스택이 둘로 갈라짐), 걷어내도 속도는 그대로였습니다. 자세한 이유는 README 의 "바이트코드 VM 을 걷어낸 이유" 절에 있습니다.
  - 나중에 진짜로 다시 만든다면 전제 조건: **모든 노드를 컴파일해 `OP_EVAL_AST` 를 없애고, 오류를 `OP_THROW` 한 길로 모을 것.** 반쯤 켠 하이브리드로 돌아가지 말 것.
  - 소스는 `c-interpreter/src_vm_backup/` 에 남겨 두었습니다.

## 2. 무엇이 Lumi 를 막고 있나 (한 문단 요약)

4단계까지 끝나서 **언어도 도구도 실무 프로젝트를 쓸 만합니다.** 남은 벽은 하나뿐이고, 그것도 언어 밖에 있습니다.

1. ~~다른 에디터~~ → `lumi lsp` + VS Code 확장(+ `lumi dap` 디버거)으로 해결.
2. ~~네트워크~~ → `bring http` (클라이언트·서버 둘 다), ~~SQLite~~ → FFI 로 해결.
3. ~~재현 가능한 빌드~~ → `lumi.lock` 으로 해결. 남은 것은 시맨틱 버전과 레지스트리.
4. ~~진짜 리눅스·맥에서 한 번도 안 돌려 봤다~~ → **CI 를 걸었습니다** (`.github/workflows/ci.yml`): 인터프리터를 우분투·맥·윈도우 셋에서, IDE 를 우분투(Qt6)에서 빌드하고 시험합니다. 남은 것은 **IDE 를 리눅스·맥에서 사람이 한 번 띄워 보는 것**뿐입니다 (CI 는 빌드까지만 봅니다).

## 3. 우선순위 원칙

이 로드맵은 **"없으면 안 굴러가는 것"을 "있으면 좋은 것"보다 앞에** 둡니다.

- 문법 설탕(패턴 매칭, 옵셔널 체이닝, 구조 분해)은 없어도 프로젝트가 굴러갑니다 → 뒤로.
- 모듈 경로, 기본값 인자, 오류 객체는 없으면 프로젝트가 안 굴러갑니다 → 앞으로.
- **모든 단계는 `tests/run.bat` 이 초록불인 상태로 끝나야 합니다.**

#### POSIX 검증에서 잡은 것 (2026-08-09)

실제로 컴파일해 보지 않았으면 못 찾았을 것들입니다.

| 무엇 | 왜 문제였나 |
|---|---|
| `realpath` · `readlink` 선언 없음 | `-std=c17` 은 엄격한 ISO C 라 POSIX 함수 선언을 숨깁니다. `platform.c` 맨 앞에 `_POSIX_C_SOURCE`/`_DEFAULT_SOURCE` 를 켜서 해결 |
| **경로 구분자 하드코딩 16곳** | `resolve_library`·`file_path_of`·`movefile`·`pkg.c` 가 `"%s\%s"` 로 이어 붙여, 리눅스에서 `libraries/` 와 패키지를 못 찾았습니다. 전부 `plat_dir_sep()` 으로 |
| **use-after-free** (`builtins.inc` format) | 놓아 준 버퍼 안을 가리키는 `key_part` 를 오류 메시지에 썼습니다. GCC `-Wuse-after-free` 가 잡음 |
| `wchar_t` 로 UTF-16 다루기 | 윈도우는 16비트, 리눅스·맥은 32비트라 뜻이 달라집니다. `uint16_t` 로 바꿔 어디서나 같게 |
| `-Wl,-z,stacksize` | Linux GNU ld 전용 옵션이라 다른 곳에서 링크가 깨집니다. 리눅스 기본 스택이 이미 8MB 라 제거 |
| iconv 링크 규칙 | 맥만 `-liconv` 로 봤는데 Cygwin·musl·BSD 도 필요합니다. `build.sh` 는 양쪽 시도, CMake 는 `find_package(Iconv)` |

덤으로 GCC 경고를 따라 죽은 코드(`obj_retain`·`instantiate`·`has_error`·`arg_idx`)도 걷어냈습니다.

#### 3.1 LSP 서버 ✅ 완료 (2026-08-09)

`lumi lsp` 가 표준 LSP 서버입니다 (`src/lsp.c`). JSON 은 인터프리터가 이미 갖고 있던 것을 그대로 씁니다.

| 해 주는 일 | 어떻게 |
|---|---|
| 문법 오류 표시 | 바뀔 때마다 **진짜 렉서·파서**를 돌려 그 줄을 짚어 줍니다 |
| 자동완성 | 내장 낱말 160개 + 그 파일의 `func`/`class`/`val` |
| 설명 보기 | 낱말 표의 쓰는 형식 |
| 파일 안 목록 | `func`/`class` 개요 |

**중복을 없앤 것이 핵심**: 낱말 표가 IDE 의 C++ 안에만 있어 LSP 가 베껴 쓸 뻔했는데, `src/lumiwords.h` 한 곳으로 옮겨 **LSP · Lumina IDE · VS Code 색칠 셋이 같은 표**를 보게 했습니다. VS Code 색칠 파일은 그 표에서 `make-grammar.py` 로 생성합니다 — 손으로 적는 곳이 한 군데도 없습니다.

**VS Code 확장** (`editors/vscode-lumi/`): `npm install` 없이 폴더만 복사하면 됩니다. 받아 오는 꾸러미가 하나도 없습니다.

#### 3.2a `lumi lint` ✅ 완료 (2026-08-09)

`lumi lint [파일|폴더]` (`src/lint.c`). 실행하지 않고 AST 를 두 바퀴 훑습니다. 찾은 게 있으면 종료 코드 1.

| # | 규칙 | 어디서 나온 규칙인가 |
|---|---|---|
| ① | 내 함수·클래스가 **내장 이름을 가림** | `func run()` 이 새 내장 `run` 에 말없이 가려져 예제가 깨졌던 사고 |
| ② | `catch` 의 **오류 종류 이름이 낯설다** | 오타면 그 절이 **한 번도 안 돕니다** — 가장 위험한 부류 |
| ③ | `return`/`break`/`continue` **뒤의 줄** | |
| ④ | **매개변수 이름 겹침** | |
| ⑤ | 딕셔너리 **같은 키 두 번** | |
| ⑥ | **안 쓰는 `bring`** | |

**설계에서 신경 쓴 것**

- **LSP 가 이미 있어 값이 두 배입니다.** `publish_diagnostics` 가 이제 `lint_source()` 를 부릅니다 — 편집기에서 **타이핑하는 대로 노란 밑줄**이 뜹니다. 파서를 두 번 돌리지 않도록 LSP 쪽 파싱은 아예 lint 에 넘겼습니다 (`-1` 이 오면 문법 오류).
- **거짓 경고를 없애는 데 규칙 하나를 더 썼습니다.** ①은 처음엔 `libraries/math.lumi` 의 `func pow` 를 나무랐는데, 그건 `math.pow(2,3)` 로만 불려 가려질 일이 없습니다. 그래서 **그 파일이 그 이름을 맨이름으로 부를 때만** 말하도록 첫 바퀴에 호출 이름을 모읍니다. `val sum = 0` 도 마찬가지로 조용합니다 (값은 불리지 않으니까 — 함수를 담은 `val` 만 잡습니다).
- **안 쓰는 변수는 일부러 뺐습니다.** 거짓 경고가 잦으면 사람들이 lint 를 통째로 꺼 버립니다.
- 시험: `tests/lint/bad.lumi` 가 여섯 규칙을 하나씩 일부러 어겨 두었고 출력이 골든입니다. 더불어 `run.bat` 이 **`examples/` 와 `libraries/` 는 lint 가 깨끗해야 한다**고 못박습니다 — lint 가 멀쩡한 코드에 짖기 시작하면 거기서 잡힙니다.

#### 3.2b `lumi fmt` ✅ 완료 (2026-08-09)

`lumi fmt [파일|폴더] [--check]` (`src/fmt.c`). **AST 가 아니라 토큰 흐름**을 다시 찍습니다.

**먼저 해야 했던 일**: 렉서가 주석을 통째로 버리고 있었습니다 (`T_COMMENT` 가 없었습니다). AST 재출력 방식으로 만들었다면 포매터가 **사용자 주석을 다 먹었을 것**입니다. 그래서 `tokenize_keep_source()` 를 새로 냈습니다 — 주석을 토큰으로 내보내고, 숫자·글자의 **원문 그대로**와 토큰마다의 **칸 수**를 함께 담습니다. 이 길은 fmt 만 씁니다(깃발 하나로 갈라 두어서 평소 렉싱 경로는 한 바이트도 안 달라집니다).

**범위를 좁힌 것이 핵심입니다** — 줄 안의 빈칸과 줄의 들여쓰기만 손대고, **줄을 붙이거나 자르지 않습니다.** 여러 줄 딕셔너리, 세로로 맞춘 줄 끝 주석, 괄호 안 이어 쓴 줄의 칸 수, CRLF 줄 끝을 모두 지킵니다. 줄 나누는 자리는 사람이 뜻을 담아 고른 것이라, 처음에 한 단계씩 계산해서 다시 밀어 넣어 봤더니 실제로 더 나빠졌습니다.

**만들며 걸렸던 것들** (전부 `examples/` 대조로 잡았습니다)

| 겪은 것 | 왜 그랬나 |
|---|---|
| `print (x)` | `print`·`error` 가 문법 낱말이라 `if (x)` 와 한 갈래로 묶였습니다 → `lumiwords.h` 의 갈래로 구분 |
| `a +(b)` | `+` 가 부호인지 두 값을 잇는 것인지 앞 토큰만 보고 판단했습니다 → 부호 여부를 다음 바퀴로 넘김 |
| `xs[0: 2]` | 자르기 `:` 과 딕셔너리 `:` 을 안 갈랐습니다 → 괄호 종류로 판단 |
| `func x:x*2` | 이름 없는 기능의 `:` 도 갈라야 했습니다 → 괄호 깊이별 `func` 깃발 |
| 여러 줄 딕셔너리가 한 줄로 | 렉서가 괄호 안 줄바꿈을 삼킵니다 → 원래 줄 번호로 되살림 |
| CRLF 가 `\r\r\n` 으로 | 주석 원문을 줄 끝까지 잘라 와서 `\r` 이 딸려 왔습니다 |

**시험**: `examples/`·`libraries/` 에 `fmt --check` 가 **아무것도 안 바뀐다**고 해야 하고(포매터가 멀쩡한 코드를 흐트러뜨리면 여기서 잡힙니다), 일부러 지저분한 `tests/fmt/messy.src` 는 다듬은 결과가 골든과 같아야 합니다. 이 두 시험이 멱등성도 함께 확인해 줍니다.

**HTTP 를 이렇게 정한 까닭 (2026-08-09)**

`https` 를 직접 하려면 TLS 암호와 **루트 인증서 저장소**가 필요한데, 후자가 운영체제마다 제각각이라 조금만 틀려도 *동작은 하는데 안전하지 않은* 상태가 됩니다. 그렇다고 libcurl 을 필수로 걸면 "그냥 컴파일되는 몇 개 파일"이라는 성질과 `cc *.c` 한 줄 빌드를 잃습니다.

그래서 **클라이언트는 `curl` 을 불러서 쓰고(`libraries/http.lumi`), 서버는 소켓으로 직접** 만들었습니다.
- curl 은 윈도우 10·맥·대부분 리눅스에 **기본 탑재**입니다. 실제로 `C:\Windows\System32\curl.exe` 가 있습니다.
- 주소를 셸이 아니라 **curl 설정 파일**로 건네 명령 주입 위험을 없앴습니다. 다만 **경로는 명령줄로** 넘깁니다 — curl 이 설정 파일을 UTF-8 로 읽지 않아 한글 경로가 깨지기 때문입니다.
- **비대칭을 이용했습니다**: 클라이언트는 TLS 때문에 어렵지만 **서버는 소켓만 있으면 되어 쉽습니다**(의존성 0).

**한계 (문서에 적어 두었습니다)**: curl 이 없는 환경(Alpine 등)에서는 못 씁니다, 요청마다 프로세스 20~50ms, 연결 재사용·스트리밍 없음.

**나중에 네이티브로 바꾼다면**: `http.get`/`http.post` **API 는 그대로 두고** 안쪽만 윈도우=WinHTTP, 맥·리눅스=libcurl 로 갈아끼우면 됩니다. 사용자 코드는 한 줄도 안 바뀝니다. 초당 수백 요청·스트리밍이 필요해질 때 하세요.

**SQLite**: sqlite3.c 한 파일(약 25만 줄)을 넣으면 되지만, 저장소 크기와 빌드 시간이 확 늘어납니다. 아직 별도 결정이 필요합니다.

#### 4.1 C FFI ✅ 완료 (2026-08-09)

`.dll`/`.so`/`.dylib` 를 열어 그 안의 C 함수를 직접 부릅니다. 내장 10 개 (`src/ffi.c` + `platform.c` 의 `plat_dlopen`/`dlsym`).

**설계에서 정한 것 — "ccall 은 배관이고, 물건은 라이브러리다."** FFI 는 본성상 위험합니다(서명 한 글자만 틀려도 프로세스가 죽습니다). 그래서 안전하게 만들려 애쓰는 대신, **보통 쓰는 사람이 볼 일이 없게** 했습니다. `libraries/sqlite.lumi` 가 그 본보기입니다 — 전부 Lumi 로 적혀 있고, 잘못 써도 `DatabaseError` 가 날 뿐 죽지 않습니다.

**서명**: `"인자들>돌려주는것"` — `i` `l` `p` `s` `b` `d` `v`.

**제약 둘과 그 까닭**
- 인자 여덟 개까지. 여덟 칸 원형 하나로 부릅니다 — x86-64(SysV·Win64)는 부르는 쪽이 스택을 치우고 arm64 는 x0~x7 에 딱 맞아서, 인자를 적게 받는 함수에 여덟 개를 넘겨도 됩니다. (32비트 stdcall 은 안 되지만 Lumi 는 64비트만 지원합니다.)
- **실수는 마지막 인자일 때만.** 실수는 다른 레지스터로 가고 윈도우 ABI 는 그 자리를 **인자 번호**로 정합니다. 자리마다 정수/실수를 골라 맞추려면 2ⁿ 가지 원형이 필요합니다(libffi 가 하는 일). 실제로 필요한 모양은 거의 `f(..., 실수)` 하나라 — `sqlite3_bind_double`, `sqlite3_result_double` — 인자 개수별 원형 12 개만 적어 두었습니다.

**값싸게 막을 수 있는 것은 막았습니다**: `cfree` 는 `cbuf` 가 준 주소만 받고(아무 정수나 free 하면 그 자리에서 죽습니다), 두 번 놓아주면 오류, 서명의 인자 개수·함수 이름은 부르기 전에 확인합니다.

**시험**: `tests/lang/ffi_test.lumi` 15 개. SQLite 가 없는 곳에서는 **건너뜁니다** — 없는 것과 깨진 것을 구별해야 하기 때문입니다. 윈도우는 `winsqlite3.dll`, POSIX 는 MSYS2 의 libc(`strlen`/`abs`/`sqrt`/`getenv`)로 양쪽 경로를 다 확인했습니다.

#### 4.2 SQLite ✅ 완료 (2026-08-09) — FFI 의 첫 손님

3단계에서 미뤄 둔 것입니다. **저장소에 `sqlite3.c` 25만 줄을 넣지 않았습니다.** 대신 운영체제에 이미 있는 것을 빌려 씁니다 — 윈도우 10 이상 `winsqlite3.dll`(이 PC 에서 확인), 맥 `libsqlite3.dylib`, 리눅스 `libsqlite3.so`.

그 대가로 소스는 **0 줄**, 빌드 시간은 **0 초** 늘었습니다. 벤더링했다면 소스가 16 배(15,608 → 약 26만 줄), 빌드가 7 초 → 40~70 초가 됐을 것입니다.

`libraries/sqlite.lumi`: `open` `close` `run` `rows` `one` `value` `tx` `lastid` `tables` `hastable` `version`. 값은 **반드시 `?` 자리로** 넘기게 해서 SQL 주입을 막았고, 자료형은 `none↔NULL`·`int↔INTEGER`·`float↔REAL`·`str↔TEXT`·`bytes↔BLOB` 로 1:1 입니다. 새 오류 종류 `DatabaseError` 를 갈래 표에 넣었습니다.

**아직 안 되는 것**: `lumi build` 로 만든 단독 실행 파일을 SQLite 없는 컴퓨터에 주면 안 돕니다. 그게 주된 쓰임새가 되면 그때 벤더링(A안)을 다시 생각하세요.

#### 4.4 문법 설탕 — `?.` 와 `??` ✅ 완료 (2026-08-10)

`a?.b` (앞이 `none` 이면 `none`) 와 `a ?? b` (`none` 일 때만 오른쪽) 둘뿐입니다. 렉서의 두 글자 연산자 표에 두 줄, 파서에 `nullish` 단계 하나, 인터프리터에 분기 둘 — 그게 전부입니다.

**정한 것 두 가지.**

- **`?.` 는 마디마다입니다.** `a?.b.c` 는 `b` 가 `none` 이면 오류입니다 (다른 언어의 "한 번 만나면 그 줄 전체가 멈춤"과 다릅니다). 줄 전체를 멈추려면 셈하는 도중에 "이 값은 `?.` 에서 나온 none 이다"를 들고 다녀야 하는데, 그 표시를 위해 `Value` 를 늘리거나 셈 경로에 깃발을 얹을 만한 값은 아니었습니다. 마디마다 붙이면 되고, 그편이 어디서 멈추는지도 눈에 보입니다.
- **`??` 는 `or` 보다 붙고 `and` 보다 헐겁습니다.** `false or none ?? 1` 은 `false or (none ?? 1)` 입니다.
- `a?.b = 1` 은 오류입니다 (`?.` 는 읽기 전용).

시험 `tests/lang/sugar_test.lumi` 9 개, 예제 `examples/sugar.lumi`.

#### 4.5 골라 쓰는(gradual) 정적 타입 ✅ 완료 (2026-08-10)

```
func 나이말하기(str 이름, int 살) str:
    return 이름 + "은(는) " + str(살) + "살"
```

매개변수 앞과 `)` 뒤에 자료형 이름을 **적고 싶은 곳에만** 적습니다. 하나도 안 적으면 예전과 한 글자도 다르지 않습니다.

**핵심은 규칙을 새로 만들지 않은 것입니다.** 검사는 `int x = 5` 선언이 쓰던 `coerce_to_type` 을 **그대로** 부릅니다 — 그래서 "선언에서는 이런데 인자에서는 저렇다" 가 생길 수 없습니다. 매개변수는 인자를 자리에 놓은 뒤(기본값 포함), 반환은 함수가 끝날 때 봅니다.

**자료형 이름이 8 개에서 12 개로 늘었습니다.** `bool` `list` `tuple` `dict` 는 형 변환 함수로만 쓰던 이름이었는데, 이것들 없이는 실제 코드에 붙일 자료형이 모자랐습니다. 넷은 **값을 다듬지 않고 맞는지만** 봅니다 (`bool b = 1` 은 오류) — `true` 와 `1` 을 섞기 시작하면 헷갈리는 곳이 너무 많아집니다. 덤으로 선언에도 쓸 수 있게 되었습니다.

**실행 전 검사기는 새로 만들지 않고 `lumi lint` 에 규칙 ⑦로 넣었습니다.** LSP 가 이미 lint 를 돌리고 있어서, 그 한 줄로 **편집기에서 타이핑하는 대로 노란 밑줄**이 붙습니다. 대신 볼 수 있는 것은 **그 자리에 글자로 적어 둔 값**뿐입니다 — 변수에 담아 넘긴 것은 조용히 넘어갑니다. 거짓 경고를 내느니 놓치는 쪽을 골랐습니다 (3.2a 의 잣대와 같습니다).

시험 `tests/lang/types_test.lumi` 12 개, 예제 `examples/types.lumi`, lint 골든에 세 줄 추가.

#### 4.6 디버거 ✅ 완료 (2026-08-10)

`lumi dap` 이 표준 **DAP**(Debug Adapter Protocol) 서버입니다 (`src/dap.c`). 봉투가 LSP 와 똑같아서 주고받는 배관은 `lsp.c` 를 그대로 본떴습니다.

| 되는 것 | 어떻게 |
|---|---|
| 중단점 · 한 줄씩(넘어가기/들어가기/나가기) · 이어 하기 | `interp.c` 의 `lumi_debug_hook` 이 문장 하나를 실행하기 **직전**마다 불립니다 |
| 호출 자취 | 이미 있던 `in->frames` 를 그대로 씁니다 (스택 트레이스와 같은 자료) |
| 겹마다의 변수 | `CallFrame` 에 `Env *env` 한 칸을 더해, 갈고리가 문장마다 적어 둡니다 |
| 값 펼치기 · 식 값 보기 | 리스트·딕셔너리·객체를 펼치고, 멈춘 자리의 환경에서 식을 셈합니다 |

**평소 실행에 드는 값은 `if (lumi_debug_hook)` 한 번뿐입니다.**

**한계 둘 — 실이 하나이기 때문입니다.** 디버거와 프로그램이 같은 실에서 돌아서 (1) 돌고 있는 도중의 `pause` 와 (2) 프로그램의 `input()` 이 안 됩니다(표준입력이 편집기와 이야기하는 통로입니다). 둘 다 읽는 쪽을 실 하나에 더 태우면 되지만, 디버거에서 '실 하나' 의 안전함이 그 값보다 큽니다.

VS Code 확장에 `debuggers` 기여와 어댑터 팩토리를 넣어 **F5 로 바로** 됩니다 (`launch.json` 없이도).

**시험**: 미리 적어 둔 DAP 대화(`tests/dap/session.txt`)를 `lumi dap` 에 흘려 넣고 답 전체를 골든과 바이트로 견줍니다. 중단점 적중 · 호출 자취 두 겹 · 함수 안의 지역 변수 · `evaluate` · `stepIn` · `continue` 가 한 판에 다 들어 있습니다.

#### 4.8 IDE 크로스 플랫폼 🟡 코드는 끝, 확인은 남음 (2026-08-10)

윈도우 전용이던 자리를 **`ide-cpp/src/core/hostenv.{h,cpp}` 한 곳으로** 모았습니다. 인터프리터의 `platform.c` 가 `plat_*` 뒤에 운영체제 차이를 숨긴 것과 같은 모양입니다 — 나머지 IDE 코드는 이제 `cmd.exe`·`taskkill`·`"C:\"` 를 **직접 알지 못합니다**.

| 갈라지는 것 | 윈도우 | 리눅스·맥 |
|---|---|---|
| 실행 파일 이름 | `lumi.exe` | `lumi` |
| 아래 터미널이 쓰는 셸 | `cmd.exe /q /k chcp 65001` | `/bin/sh -i` |
| 줄 끝 | `\r\n` | `\n` |
| 폴더 옮기기 | `cd /d "..."` | `cd "..."` |
| 트리째 죽이기 | `taskkill /T /F /PID` | 무리(process group)에 `SIGTERM`→`SIGKILL` |
| 터미널 첫 폴더 | `C:\` | 홈 폴더 |
| 프롬프트 알아보기 | `C:\...>` | `\w$ ` (PS1 을 우리가 못박습니다) |

**정한 것 두 가지.**

- **`$SHELL` 이 아니라 `/bin/sh` 를 씁니다.** 윈도우가 사람이 고른 셸이 아니라 `cmd.exe` 를 쓰는 것과 같은 이유이고, 더 중요하게는 프롬프트를 못박을 수 있어서입니다 — 대화형 `bash` 는 `~/.bashrc` 를 읽어 우리가 넣어 준 `PS1` 을 도로 덮어씁니다. 프롬프트를 못 알아보면 아래 터미널이 첫 화면부터 어긋납니다.
- **트리째 죽이기는 무리(process group)로 합니다.** 자식을 `setsid()` 로 제 무리의 우두머리로 세워 두고 음수 pid 로 죽입니다 — 손자까지 함께 갑니다. `pkill -P` 는 손자를 놓칩니다.

**빌드**: `CMakeLists.txt` 에서 `WIN32_EXECUTABLE` 과 `.rc` 를 윈도우에서만 붙이고, 맥은 `MACOSX_BUNDLE` 로, 컴파일 옵션은 MSVC/그 밖으로 갈랐습니다. `ide-cpp/build.sh` 를 새로 두어 리눅스·맥에서 `./build.sh` 한 줄이면 됩니다 (인터프리터가 아직 없으면 그것부터 빌드합니다).

**덤으로 잡은 것 — 동시성이 심어 둔 이식성 구멍 둘.** 리눅스·맥 빌드에 **pthread 를 이어 주지 않고 있었습니다** (`CMakeLists.txt` 에 `find_package(Threads)`, `build.sh` 에 `-lpthread` 추가). 그리고 `dap.c` 가 `lumi_err_msg`/`lumi_err_trace` 를 **실마다 따로**(`LUMI_TLS`) 표시 없이 다시 선언하고 있었습니다 — MSVC 는 넘어갔지만 GCC 는 오류입니다. 둘 다 MSYS2 로 POSIX 분기를 실제로 빌드해 보고 나서야 나왔습니다.

**어디까지 확인했나 (정직하게)**

| 확인한 것 | 어떻게 |
|---|---|
| 인터프리터 POSIX 분기 — 빌드·동작 | MSYS2 gcc 15.2 로 빌드. **언어 단위시험 109/109 통과**, `examples/concurrency.lumi` 가 실제로 겹쳐 돌고, DAP 대화가 윈도우 골든과 **바이트 단위로 동일** |
| IDE POSIX 분기 — 헤더와 무늬 | `kill`/`setsid` 가 **엄격한 `-std=c++17`** 에서도 보이는지 따로 컴파일해 확인(그래서 `_POSIX_C_SOURCE` 를 켰습니다), 프롬프트 무늬는 실제 프롬프트 글자들로 맞춰 봄 |
| IDE 윈도우 — 회귀 없음 | 다시 빌드 + `ide-cpp/tests/run.bat` 통과 |
| **IDE 를 리눅스·맥에서 실제로 띄워 보기** | **못 했습니다.** 이 PC 에 리눅스용 Qt6 이 없습니다 |

즉 **IDE 의 리눅스·맥 쪽은 "적어 두었고 앞뒤가 맞지만, 아직 아무도 띄워 보지 않은" 상태**입니다. 남은 일은 우분투/맥에서 `ide-cpp/build.sh` 를 한 번 돌려 보고, 아래 터미널의 프롬프트·`cd`·Stop(트리째 죽이기)·F5 네 가지를 눈으로 확인하는 것입니다. 그때까지 표의 상태는 ✅ 가 아니라 🟡 입니다.

#### 4.7 동시성 ✅ 완료 (2026-08-10)

내장 **둘뿐**입니다: `start(부를것, 값...)` → 일감(새 값 갈래 `task`), `wait(일감)` → 그 값.

**고른 길: 진짜 OS 실 + 큰 자물쇠 하나(GIL).** 자리를 내주는 곳은 **`sleep` 과 `shell` 뿐**입니다.

| 왜 이 길인가 | |
|---|---|
| 참조 세기·순환 수집기·`g_gc_head` 가 전부 **한 줄기 전제** | 자물쇠를 잘게 쪼개면 조용히 깨지는 버그가 들어옵니다 |
| Lumi 가 실제로 쓰이는 곳은 거의 다 **기다리는 일** | 자동화·CLI·`bring http`(= `shell` 로 curl) |
| `sleep`·`shell` 사이가 안 끊김 | **mutex 를 언어에 넣지 않아도 됩니다** — 내장이 둘로 끝난 진짜 까닭 |

**바꾼 것**: 오류 자리(`lumi_err_msg`/`lumi_err_trace`/`lumi_err_kind`/`lumi_jmp`/`g_current_interp`)를 **실마다 따로**(`LUMI_TLS`)로. 일감마다 제 `Interp` 를 두되 **`globals` 는 부모와 함께** 씁니다. `platform.c` 에 `plat_gil_lock`/`unlock` 과 `plat_thread_start`/`join` (윈도우는 SRWLOCK + `_beginthreadex`, POSIX 는 pthread; 되돌이가 깊어질 수 있어 **자리 8MB**로 본 실과 같게).

**정한 것**: 일감의 오류는 그 자리에서 뜨지 않고 **`wait` 자리에서 종류째로 다시 납니다**(`catch ValueError e:` 로 잡힙니다). 같은 일감을 **여러 번 기다려도** 됩니다. 아무도 안 기다린 일감은 값이 사라질 때 끝날 때까지 기다렸다 치웁니다 — 놓친 실이 남지 않습니다.

**안 되는 것**: 셈만 하는 일은 안 겹칩니다(설계대로). `gc()` 는 일감이 도는 동안 부르지 마세요.

시험 `tests/lang/concurrency_test.lumi` 4 개, 예제 `examples/concurrency.lumi` (하나씩 돌린 시간과 따로 돌린 시간을 **한 판에서 견주어** 기계 속도와 상관없이 참이 되게 했습니다).
